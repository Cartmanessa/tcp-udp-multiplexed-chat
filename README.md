# tcp-udp-multiplexed-chat

Четыре клиент-серверные программы на C/C++, которые пересылают текстовые сообщения с датой и временем по собственному бинарному протоколу поверх TCP и поверх UDP. Каждый сервер обслуживает несколько клиентов (или несколько портов) в одном потоке, без создания новых потоков на клиента — через мультиплексирование ввода-вывода (`poll()` на Linux, `select()` на Windows).

| Файл | Платформа | Компилятор | Роль |
| --- | --- | --- | --- |
| `tcpclient.cpp` | Windows | MSVC | читает файл сообщений, шлёт их на TCP-сервер, ждёт подтверждений |
| `tcpserver.cpp` | Linux | g++ | принимает до 64 клиентов одновременно через `poll()`, пишет лог в `msg.txt` |
| `udpclient.cpp` | Linux | g++ | рассылает UDP-дейтаграммы с повторной отправкой до получения подтверждений |
| `udpserver.cpp` | Windows | MSVC | слушает диапазон UDP-портов через `select()`, ведёт базу клиентов с защитой от дублей |

## Формат входного файла

Каждая строка — одно сообщение:

```
ДД.ММ.ГГГГ ДД.ММ.ГГГГ ЧЧ:ММ:СС Текст сообщения
```

Например:

```
01.01.2000 01.01.2001 00:00:00 hello
01.01.2000 01.01.2001 00:00:01 world
01.01.2000 01.01.2001 00:00:02 stop
```

Пустые и некорректные строки (неверный диапазон даты/времени, отсутствующие поля) клиенты пропускают с сообщением в stdout. Сообщение с текстом `stop` — служебное: получив его, оба сервера штатно завершают работу.

## Бинарный протокол

Одно сообщение кодируется в 16+ байт, одинаково для TCP и UDP:

| Поле | Размер | Формат |
| --- | --- | --- |
| номер сообщения | 4 байта | `uint32`, сетевой порядок байт (`htonl`/`ntohl`) |
| день даты 1 | 1 байт | |
| месяц даты 1 | 1 байт | |
| год даты 1 | 2 байта | `uint16`, сетевой порядок (`htons`/`ntohs`) |
| день даты 2 | 1 байт | |
| месяц даты 2 | 1 байт | |
| год даты 2 | 2 байта | сетевой порядок |
| часы | 1 байт | |
| минуты | 1 байт | |
| секунды | 1 байт | |
| текст сообщения | переменная длина | без завершающего `\0` |
| терминатор | 1 байт | `0x00` |

**TCP.** После установления соединения клиент сразу шлёт 3-байтовую команду `put`, затем — поток кадров один за другим (без ожидания подтверждения между ними, то есть пайплайном). Сервер отвечает `ok` (2 байта) на каждый принятый и записанный в лог кадр; клиент не завершает работу, пока не получит подтверждение на все отправленные сообщения. Команда `get` переводит сервер в режим отдачи: он кодирует всё содержимое `msg.txt` в такие же бинарные кадры и передаёт их клиенту, после чего закрывает соединение. В этом репозитории `tcpclient.cpp` отправляет только `put` — `get` реализован на стороне сервера для другого клиента (например, инструмента чтения лога).

**UDP.** Команды `put`/`get` не используются — клиент сразу шлёт кадры дейтаграммами. Если какие-то дейтаграммы теряются, сервер просто не увидит эти номера; за повтор отвечает клиент. Сервер в ответ на каждую дейтаграмму отправляет список последних до 20 принятых от этого клиента номеров (по 4 байта, сетевой порядок, без дополнительных полей). Клиент вычёркивает подтверждённые номера и раз в 100 мс повторяет отправку того, что ещё не подтверждено, пока не наберёт нужное число подтверждений (20 или меньше, если сообщений в файле меньше 20).

## Архитектура серверов

**TCP-сервер (`poll()`, Linux).** Слушающий сокет и до 64 клиентских сокетов в неблокирующем режиме. На каждой итерации главного цикла собирается массив `pollfd`, `poll()` ждёт события до 500 мс. Для каждого клиента хранится структура `TcpSession`: входной кольцевой буфер на 600 КБ (TCP может фрагментировать данные, поэтому заголовок кадра может прийти не целиком), состояние разбора протокола (`SESS_CMD_PENDING` → `SESS_PUT_MODE` или `SESS_GET_MODE`) и поля для досылки «ok», если `send()` в неблокирующем режиме успел отправить не все 2 байта. При отключении клиента запись сдвигается из массива `memmove`-ом, поэтому обход в главном цикле идёт с конца к началу — иначе после удаления элемента следующий за ним пропускался бы.

**UDP-сервер (`select()`, Windows).** На каждый порт из диапазона создаётся свой неблокирующий UDP-сокет. База клиентов — массив из 256 записей `PeerEntry`, ключ — строка `IP:port`; один клиент опознаётся одинаково независимо от того, на какой из портов он прислал дейтаграмму. Для каждого клиента хранится до 1024 последних номеров принятых сообщений — по ним определяются дубликаты. Раз в секунду клиенты без активности дольше 30 секунд удаляются из базы.

**TCP-клиент (Windows).** Подключается с повторными попытками (до 10, с паузой 100 мс), разбирает входной файл с полной валидацией полей, пакует сообщения через `malloc`, досылает их гарантированными обёртками `tcp_write_full`/`tcp_read_full` (TCP не гарантирует, что один вызов `send`/`recv` обработает все запрошенные байты).

**UDP-клиент (Linux).** Загружает все сообщения из файла в память (до 100 000 штук), затем в цикле: отправляет все ещё не подтверждённые дейтаграммы → ждёт ответ до 100 мс через `select()` → отмечает подтверждённые номера → повторяет, пока не наберёт нужное число подтверждений.

## Сборка

**Windows (`tcpclient.cpp`, `udpserver.cpp`)** — из «Developer Command Prompt for VS»:

```
cl /EHsc tcpclient.cpp /link ws2_32.lib
cl /EHsc udpserver.cpp /link ws2_32.lib
```

**Linux (`tcpserver.cpp`, `udpclient.cpp`)**:

```
g++ -O2 -o tcpserver tcpserver.cpp
g++ -O2 -o udpclient udpclient.cpp
```

## Запуск

```
# на Linux
./tcpserver 9000

# на Windows
udpserver.exe 9000 9000

# на Windows — отправить файл сообщений на TCP-сервер
tcpclient.exe 192.168.1.10:9000 messages.txt

# на Linux — отправить файл сообщений на UDP-сервер
./udpclient 192.168.1.20:9000 messages.txt
```

`udpserver` принимает диапазон портов: `udpserver.exe 9000 9005` слушает сразу 6 портов (9000–9005). Для одного порта оба аргумента должны совпадать.

Оба сервера пишут принятые сообщения в `msg.txt` рядом с собой, с префиксом `IP:port` отправителя.

## Тестирование как проводилось

Проверено в реальной сети: ноутбук с Windows обращался к Linux-машине (UTM на Mac) по Wi-Fi. Тесты включали штатные сценарии, граничные значения дат (от `01.01.0000` до `31.12.9999`), очень длинные сообщения, пустые и некорректные строки, а также нагрузочный сценарий с тысячей сообщений подряд.
